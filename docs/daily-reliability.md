# 每日刷新可靠性规则 — 2026-10-23

本次加强的是运行可靠性；已有的 Active 更新发现、官方详情当前 PDF、独立字节核验继续保留。

## 调度和验收

每天 UTC 10:23 和 22:23（北京时间 18:23、06:23）抓取。随后自动进行官方当前版本对账，再独立下载 PDF 核验。只有源站读取、当前版本覆盖和实际字节核验都通过，才推进 `data/last-successful-verification.json`。没有新报告可以正常，长期没有成功核验不能算正常。

官方详情缓存至多在同一个 UTC 日内复用六小时；即便 URL、报告编号和缓存哈希不变，对账仍重新下载当前 PDF。回归测试禁止以本地缓存有效代替源站当前字节核验。

恢复窗口取七天和“上次成功独立核验日至今加一天重叠”之间的较大值。显式指定历史结束日期的手动任务不被改写。超出支持范围会报错，不静默截断。未发布、未被公开源发现的资料不在可证明的完整性范围内。

## 独立看门狗

每小时第 17 分钟，以及生产工作流结束后，检查抓取、官方对账、独立核验三阶段及其真实凭证。超过 26 小时无成功证据、最新运行失败、官方待办未清或文件缺失／不可核验时，`HEALTH.md` 和 `data/health.json` 明确显示异常。

距最后抓取超过 14 小时可补触发；链路断开超过两小时可补触发下游阶段。重试遵守每阶段六小时冷却、合计每 24 小时最多四次；已有流程在运行时不重复启动。不会自动重新启用被用户手动停用的工作流。失败不因派发了重试就被标成完成。

异常创建或更新一个带固定标识的 GitHub Issue，并提及仓库所有者；恢复后关闭。用户能否收到邮件／推送仍取决于 GitHub 通知设置。API、权限或整个 GitHub 不可用时，本平台内看门狗也可能无法发送告警，需平台外检查作为补充。

`data/health.json.checked_at` 只是监控时间，不能充当源站刷新时间。每小时健康记录提交不计作报告更新。

## 防回归

拉取请求和代码变更会执行只读离线测试。覆盖旧封面日期仍有 Active 更新、镜像落后、同日不同 PDF、实际哈希损坏、缺少官方来源、旧运行凭证、无新报告、26 小时断档、重试冷却和长断档追赶。工作流 Artifact 名称包含 run ID 和 attempt，防止旧重跑分片混入。

这不是永久不故障的保证。GitHub 定时任务可能延迟或被丢弃，上游也可能限流、改接口或暂时下线。这里提供的是多次运行机会、真实可核验的完成记录、异常告警和有界恢复。公开 DEMO_KEY 仍可能限流；推荐在仓库 Secret 中配置个人 `CONGRESS_API_KEY`，不要提交到源码。
