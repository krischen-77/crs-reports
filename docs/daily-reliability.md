# 每日刷新可靠性规则 — 更新于 2026-10-28

Active 更新发现、官方当前原文解析和独立字节核验继续保留。通知与内容健康分开判断：降低可恢复问题的通知频率，不降低完整性标准。详见[每日交付与降噪告警规则](delivery-alert-policy.md)。

## 调度和验收

每天 UTC 10:23 和 22:23（北京时间 18:23、06:23）抓取。随后进行官方当前版本对账，再独立下载原文核验。当前阶段正常执行、完整性检查通过且真实结果已持久化后，即使有单份可恢复来源失败，也继续下游独立对账；不得让一条旧镜像失败反复阻断整条链路。

只有源站读取、当前版本覆盖和实际字节核验都通过，才推进 `data/last-successful-verification.json`。部分结果仍如实记录缺失，不因 Actions 执行成功就宣称覆盖完整。没有新报告可以正常，长期没有成功核验不能算正常。

官方详情缓存依据真实经过时间最多复用六小时，跨 UTC 午夜本身不会使其过期；即便 URL、报告编号和缓存哈希不变，对账仍重新下载当前原文。回归测试禁止以本地缓存有效代替源站当前字节核验。

恢复窗口取七天和“上次成功独立核验日至今加一天重叠”之间的较大值。显式指定历史结束日期的手动任务不被改写。超出支持范围会报错，不静默截断。未发布、未被公开源发现的资料不在可证明的完整性范围内。

## 独立看门狗与有界恢复

每小时第 17 分钟，以及生产工作流结束后，检查抓取、官方对账、独立核验三阶段及其真实凭据。超过 26 小时无成功证据、最新运行失败、官方待办未清或文件缺失／不可核验时，`HEALTH.md` 和 `data/health.json` 继续明确显示异常，不把部分结果刷成 healthy。

距最后成功抓取超过 14 小时可补触发；链路断开超过两小时可补触发下游阶段。重试遵守每阶段六小时冷却、合计每 24 小时最多四次；已有流程运行时不重复启动。不会自动重新启用被用户手动停用的工作流。失败不因派发了重试就被标成完成；正常启动未超过两小时的恢复流程，对旧成功时间暂时落后给予宽限。

`data/last-successful-collection.json`、`data/last-successful-official.json` 和 `data/last-successful-verification.json` 分别保留三个阶段的真实成功凭据。失败尝试不得覆盖成功时间；历史采集成功可从 `data/runs/` 的实际成功结果恢复，而不是从 Git 提交推断。

`data/health.json.checked_at` 只是监控时间，不能充当源站刷新时间。每小时健康记录提交不计作报告更新。

## 分级通知

单份可恢复来源失败、辅助 HTML 不可用、已披露的旧镜像差异保留 warning 与重试任务，不使每个阶段反复报错发邮件。超过 26 小时未成功刷新／核验、必需内容问题长期未解决、已保存文件损坏、工作流禁用或长时间卡住等实质故障，才集中更新一个带固定标识的 GitHub 告警 Issue；同一问题不反复创建 Issue，恢复后关闭。

代码执行异常、当前运行凭据缺失、实际文件损坏、证据或原文持久化失败仍使相应 Actions 失败，不用 continue-on-error 掩盖。GitHub 内部监控无法完成检查时也会明确失败。用户能否收到 Issue 邮件／推送仍取决于 GitHub 通知设置。

按北京时间完整自然日统计新增原文，次日08:00以后，一整天零新增只发一次交付提示。统计排除可选历史补抓，去重同一运行和尝试；提示区分源站没有新报告与有更新但未归档，不把零新增本身写成刷新失败。

API、权限或整个 GitHub 不可用时，平台内看门狗也可能无法发送告警，需平台外检查作为补充。外部监控检查调度停跑，但在源站刷新与独立核验仍新鲜、无实际交付故障时，不因短暂看门狗调度延迟单独反复打扰。

## 防回归与边界

拉取请求和代码变更执行只读离线测试。覆盖旧封面日期仍有 Active 更新、镜像落后、同日不同 PDF、实际哈希损坏、缺少官方来源、旧运行凭据、无新报告、26小时断档、重试冷却、长断档追赶、每日零新增去重，以及仅在新版官方原文已经保存并校验后才允许分离过期镜像历史任务。工作流 Artifact 名称包含 run ID 和 attempt，防止旧重跑分片混入。

这不是永久不故障的保证。GitHub 定时任务可能延迟或被丢弃，上游也可能限流、改接口或暂时下线。系统提供多次运行机会、真实可核验的完成记录、分级告警和有界恢复。公开 DEMO_KEY 仍可能限流；可在仓库 Secret 中配置个人 `CONGRESS_API_KEY`，不要提交到源码。
