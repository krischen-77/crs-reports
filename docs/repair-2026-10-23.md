用户关于“CRS 更新了，但仓库没有收进去”的质疑成立。以前只按报告发布日期窗口和抓取程序成功状态判断完整性，范围不足。2026-10-23 的深入核查发现：官方 API 本周仍在更新的 8 个 Active 报告编号，此前没有任何 PDF 归档。修复后补入 11 个 PDF 版本，累计从 464 增至 475；每份新增 PDF 均有 Markdown 全文。

不能把这 11 份说成“本周新发布的 11 份报告”。这些是本周 API 标记更新、但原封面日期较早的当前文件及来源保留版本，原始发布日期没有改写。

## 根因

1. 为避免归档状态批量变化拖垮演示 API 配额，10 月 4 日的修复把所有较旧 `publishDate` 的 API 更新都放进 metadata-only。这个判断范围过大：Active 报告的本周更新不能仅因封面日期早就被排除。
2. 失败任务按封面日期分流时，也可能把本周真实更新的旧日期报告降级成可选历史任务。
3. 对官方待重试任务，仅比较发布日期而不比较具体 PDF URL，会把不同文件修订号错误地视为已由镜像覆盖。
4. 原 `LATEST.md` 只显示发布日期落在窗口内的文件，会隐藏“本周更新但原发布日期较早”的已保存原文。

## 已实施的修复

- 将本周发布、镜像本周修订、本周有 updateDate 的 Active 报告合并为必需处理范围；仅非 Active 的老历史状态变化继续保留为 metadata-only。
- 给本周更新任务添加 `required_by_recent_update`，不因旧封面日期自动降级到历史补抓。
- 官方重试任务与镜像合并时增加具体 PDF URL 匹配，不再仅凭同日出版就取消任务。
- 保存官方 API 原始扫描记录到 `data/sources/congress-api-latest.json`，使候选范围可以复核。
- `LATEST.md` 增加第二部分 **Active reports updated in this window with older publication dates**，分别列 API 更新日期和原发布日期。
- 增加独立覆盖率检查：不复用抓取器的候选筛选函数，以官方近期发布与全部 Active 更新信号、镜像修订的并集重新核对；直接取回官方 PDF，与实际归档字节比较。来源无法获取记为 unverified，缺文件记为 failed，不以绿色抓取状态代替完整性。
- 独立检查工作流在每次 `CRS daily backup` 结束后触发，同时支持手动运行。原每日备份时间不变。
