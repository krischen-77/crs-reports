# CRS daily backup 修复记录 — 2026-10-04

## 事故与原因

核对的失败运行：2026-10-02 / `36996049567`，2026-10-03 / `37116843260`。

10 月 3 日共尝试 448 项，成功保存/复用 210 项；8 份新 PDF 实际提交成功，累计 309 个 PDF 版本。238 项报错，247 项进入重试（含辅助 HTML）。主错误为 API `HTTP 429` 及后续限流熔断，并非上传权限或仓库损坏。

旧代码把 API `updateDate` 当作新报告下载信号，纳入了数百篇 2000s—2021 年旧报告。旧镜像 PDF 校验不一致时，脚本逐份调用官方 API 解析独立原件，耗尽演示 key 配额。已经独立恢复的官方文件与旧镜像 SHA-1 不同，旧缓存判断未使用 `source_recovery`，导致下一天重复请求同一文件。

## 修改

1. 保留完整链接目录和所有 API 元数据；`publishDate` / 镜像最新修订日期识别原文窗口，纯元数据更新另存 `data/metadata-only-updates.json`。
2. 从运行记录恢复最早备份日 **2026-09-17**，该日起真正未完成的原文任务始终保留为必需重试。现有 247 项全部早于该日期，完整迁移到有审计字段的历史队列，不删除任何任务或已存文件。手动回填较早窗口时相关任务重新成为必需工作。
3. 先处理当前原文，再最多尝试 2 项历史工作；历史失败保留完整 specification、错误、次数、下一重试日，采用 2—30 日退避。
4. 仅在报告编号、发布日期、原失败来源/校验值以及本地实际 SHA-256 均匹配时复用独立恢复的官方 PDF。HTML 重试保留恢复记录和原文件路径。镜像 PDF 校验仍严格，不接受不匹配字节。
5. API 预算统计每个实际网络尝试，读取剩余配额；当前运行结果需匹配 GitHub run ID / attempt；所有 PDF 和 HTML 哈希在提交前复核。
