## 根因与修复

### 1. 旧封面日期被错误排除

10 月 4 日为处理历史 Archived 状态变化造成的请求洪峰，旧代码把许多较旧 `publishDate` 的 API 更新都归入 metadata-only。范围过大，误排除了本周仍有更新的 Active 报告。

现在把“近期发布／镜像近期修订／本周 Active 更新”纳入必需范围。较早的封面日期不会导致真实近期更新自动降级为可选历史任务。原文日期保留，不为满足窗口而改写。

### 2. 镜像版本被误当作官方最新版

镜像可能提供同编号、同日期的旧修订版。直接下载镜像所指向的官方旧 PDF 并校验通过，也只能证明那个旧文件已保存，不能证明官方当前 PDF 已保存。

新增 `tools/official_pipeline.py` 和 `official-reconcile.yml`：逐份解析官方详情接口的当前 `formats`，按它返回的 URL 下载和核验。镜像继续用于版本历史和补充发现，但不再决定“官方当前版本”。

### 3. 同日期的不同 PDF 被错误合并

原官方重试任务与镜像合并时曾只比较发布日期。现加入具体 PDF URL 与实际内容哈希核对；不同字节分别保留，不能只因同日出版就取消未完成任务。

### 4. 成功状态缺乏独立验收

现在分为三个阶段：**每日收集 → 官方当前版本对账 → 独立重新下载核验**。独立核验不复用原来的日期排除条件，不用第一阶段的绿色状态作为完整性证明。

官方详情缓存必须匹配更新信号且为当天核查证据；当日详情无法刷新不能以旧缓存掩盖。限流、来源不可读、文件损坏和未解决条目仍明确记录，部分成功原文可保存，但不完整的对账不得标成全部完成。

### 5. 列表与详情更新时间不完全一致

实测两个接口可能返回不同的 `updateDate`，不能无依据地假定其索引更新时间完全同步。现在分别保存时间戳并保留差异告警，仍要求报告编号一致、详情覆盖所需发布日期、当前 `formats` 可解析、PDF 实际字节匹配。

最终 receipt 中保留了前序诊断和时间戳差异，并不等于这些诊断从未发生；最终待核验数为 0，且独立重新下载的 68 份原文均通过。
